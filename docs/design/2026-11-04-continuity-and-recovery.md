# 下一轮：任务接续与可靠交付

本轮基于统一昔涟人格分支继续开发。陪伴、工作、代码和学习仍由同一个昔涟承担；优先解决长期使用中的任务中断、消息投递和升级恢复问题。

## 备份与实施顺序

- 起点：`0c49e1ba`，备份分支：`backup/unified-xilian-before-continuity-20261104`。
- 开发分支：`feat/xilian-continuity-20261104`。保持 `master` 与实际运行的服务器不变。
- 先完成渠道持久化与定时任务执行，再接入上下文任务笔记、具体跟进和记忆治理，最后做跨端验收。

## 架构约束

1. 会话事实仍以 CTA 为准。任务工作笔记扩展既有 `task_state`，随活动分支和压缩检查点恢复，不另建一份聊天事实库。
2. 渠道恢复库只负责收件、附件副本、投递分片与游标。它不把“开始发送”当成“已经送达”。未知结果需人工核对，不承诺网络环境下绝对恰好一次。
3. 定时任务冻结原会话、工作区、工具清单和权限上限，执行时继续受最新全局开关及权限约束。后台无法获得交互授权时停止相应工具。
4. 前台、渠道与定时任务共享每会话运行守卫。排队、取消和崩溃都必须有可恢复状态，不在整个模型运行期间占用底层数据库追加锁。
5. 相处跟进是用户明确创建的事项，具有状态和时间窗口。发出询问后等待回复，不把模糊共同目标变成重复催促。准确时刻执行操作仍属于定时任务。
6. 记忆纠错以真实来源 ID 关联。不能用语义相似度推断应删除的其他聊天；无法证明关联的旧数据明确展示限制。
7. 更新在临时工作树完成依赖和编译，再停服务备份数据；回退使用确定的提交和产物，不依赖 `HEAD@{1}`。健康检查不调用付费模型或真实渠道。

## 验收重点

| 模块 | 必须验证的边界 |
| --- | --- |
| 延时任务 | 旧提醒兼容、工具允许范围、冻结收件人、停机策略、排队取消、崩溃后未知结果 |
| 渠道恢复 | 接收去重、游标落盘顺序、部分附件送达、重启、禁用渠道、人工确认、认证接口 |
| 任务接续 | Todo 兼容、工作笔记单独更新、写入失败回滚、压缩检查点、活动分支、主/子任务恢复 |
| 具体跟进 | 创建/修改/完成/暂停/改期、旧数据迁移、路由隔离、生成中修改、等待回复不重复催促 |
| 情绪线索 | 否定表达、引用、第三人称、条件假设与直接自述区分 |
| 记忆治理 | 删除范围预览、原聊天保留、来源防重建、新来源可重新学习、跨域部分失败可恢复 |
| 更新恢复 | 构建失败不停机、停机后备份、确定版本回退、启动失败恢复、路径与并发锁 |
| Windows/Web | 四个 TypeScript 入口、双端构建、共享核心认证与持久化、窄屏设置可操作 |

## 本轮不作的承诺

本地自动验收使用隔离数据、模拟渠道和模型响应，不连接用户真实微信、B 站或远程服务器。Linux systemd 的原生验收由 Linux CI 与后续部署执行；Windows 上的故障注入不能替代它。人格自然度需要长期真实对话评价，本轮测试只证明状态、权限和接续机制。

外部插件进程隔离、统一费用预算和大规模人格对话评测留给后续轮次。本轮不修改版本号、不生成新安装包，不自动合并到 `master` 或发布线上。
