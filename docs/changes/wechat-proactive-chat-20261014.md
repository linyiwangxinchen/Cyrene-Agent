# 微信主动聊天与追加追问检查（2026-10-14）

## 检查结论

“微信绑定本地聊天”与“主动消息仅微信”此前没有完整串联。绑定本身能让普通问答共享上下文，但主动模块另有进程内收件人缓存；重启后该缓存和微信 context_token 都丢失，不能仅靠持久化绑定恢复主动投递。即使连接显示正常，也可能在投递预检查时取消。

主动生成此前取最近使用的普通会话，未优先取微信绑定的会话；发送后的主动内容只进旧渠道 JSONL，未写进正式会话轨迹。模型因此可能读取无关聊天，下一次也看不到刚刚发过的主动消息。

旧场景仅有早晚问候、离开电脑后回来、连续使用电脑后休息。一次未回复后的追问要求至少 6 小时、不同场景、评分至少 80；早晚候选扣除未回复分后达不到这个分数，几乎只能靠“离开归来”触发。无桌面的服务器、关闭浏览器后的微信用户很难获得这样的候选。

另有两个问题：策略/渠道阻挡也会消耗 30 分钟模型重试退避；主动模型调用的输出预算固定 600，在把思考计入输出预算的模型上，可能尚未输出决策 JSON 就耗尽。原设置页只显示候选分数，无法区别这些情况与模型主动选择静默。

这些是代码确认的问题，不能单凭代码认定其中某一项就是线上最近两天未发送的直接原因。需结合运行服务的设置、版本、日志和状态确认。

## 修改及设置语义

- 收件目标优先选择所选渠道唯一的持久化私聊绑定。多个私聊绑定时明确报目标不唯一，不猜测；群聊不会成为主动收件目标。没有绑定时保留当前进程最近私聊的兼容行为。
- 微信最新回复上下文按 bot 账号加密保存，重启同一账号时恢复。停用暂停发送但保留上下文；登出、账号变化或会话过期清除。文件只存服务端，不返回浏览器。30 天是本地保留策略，不代表微信保证令牌有效 30 天；微信拒绝旧上下文时仍需手机再发一条消息。
- 生成读取所选私聊绑定的正式聊天轨迹，冻结收件人与会话；模型生成过程中绑定变更则取消，不把旧上下文发给新目标。
- 主动消息实际发送成功后写回同一正式聊天，记录渠道投递结果并刷新 Web。写记录失败不会把已接受的发送误判为未发送并重发。
- 新增 `conversation_followup` 候选：用户时区 08:00–22:00，所选聊天有真实用户发言，最近活动距今 2–48 小时，可交给模型判断是否自然跟进。无需打开浏览器、无需桌面。它是生成候选，不是固定提醒文案或保证发送。
- 仍保留聊天后 30 分钟静默、主动消息至少间隔 2 小时、同场景冷却、一次未回复后至少 6 小时且不同场景/至少 80 分、连续两次未回复暂停。用户新发消息会清零未回复次数。当前没有独立“追加追问”开关，追问受同一主动聊天开关及上述规则控制。
- 目标评分仍限制 0–100，默认 60。设置 0 也不会绕过静默、冷却、未回复、连接、收件人等限制；高于实际候选评分则不会生成。模型可返回静默，不会强塞固定话术。
- 策略或渠道阻挡不会消耗模型评估退避。推理模型的主动输出上限提高到 4096，非推理/显式关闭思考仍为 600；耗尽输出预算、HTTP 错误、模型格式不对等保留明确原因。
- 偏好设置显示当前阻挡原因、投递就绪状态、最近生成/静默/发送结果与时间，以及连续未回复次数。状态为本次服务进程内信息，重启后最近处理结果重新累计。

设置需点击保存。选择“仅微信”不会改发到本地；把成功消息同步到绑定聊天记录，是保存同一消息的上下文，不是额外发送一次本地消息。

最终验证通过 49 个测试文件、385 项测试；Main、Server、Renderer 类型检查通过，Windows 主进程构建、无桌面核心构建、Web 页面构建通过。构建后的隔离认证 Web 服务通过 33 项共享核心验收，包括新加的主动设置保存与微信投递诊断。

线上限制：当前 `key.txt` 对应 SSH 连接超时。本次未更改线上配置、未重启线上服务、未向真实微信账号发送消息；不能把本地模拟链路通过表述为手机端实际验收通过。首次升级前若还没有新的加密回复上下文文件，需要从手机发一条消息后才有可恢复的上下文。

微信回复字段参考 [Tencent/openclaw-weixin 协议说明](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol.md)。协议说明不保证缺少 `context_token` 时服务端接受请求，本程序因此保留缺失上下文时停止发送的处理。
